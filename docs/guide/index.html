01The problem in one picture

Every month CDSCO, India's drug regulator, publishes lists of medicine batches whose samples failed a lab test (Not of Standard Quality, NSQ) or were found spurious. A person holding a strip cannot easily tell whether their batch is on one of those lists. StripCheck answers exactly one question: is this exact pack from a listed batch?

Trap 1: one misread character

A camera can read the final B of LM2408B as 8, and even report confidence 1.0. An exact lookup then misses the alert.

Trap 2: shared batch codes

8S17004 is listed for three different medicines. A batch match alone would false-alarm on unrelated products.

Trap 3: sibling batches

R21119 and R21719 are both listed, same drug and maker, one confusable character apart. A misread can land exactly on a listed sibling.

The only four answers StripCheck can give

FLAGGED
This batch is on an alert list

Matched an NSQ entry, batch confirmed, details corroborated. Cites the record.

SUSPECTED_FAKE
Listed as purported spurious

Matched an entry on the spurious list. Same gate as FLAGGED.

NOT_LISTED
No matching alert found

No match on the lists loaded, latest month stated. Never "safe": CDSCO tests only sampled batches. No green.

CANT_VERIFY
More evidence is needed

The agent abstains and says why (unconfirmed batch, date conflict, no data, unreadable).

Headlines are the exact strings in core/templates.py. Rule styles follow docs/design/ui_direction.md: solid, hatched, hollow, dashed. Every result ends with pharmacist advice and never says "stop taking".

02Big-picture architecture

Two kinds of work. Per check (left): a pack goes through the Investigator and the Verifier. Background (right): the Supervisor syncs the lists, ingests them and re-checks saved packs. Both share one local SQLite file.

The agents, one job each

Ingest: lists → validated alert rows, bad rows quarantined, nothing invented.

Investigator: one pack → candidates → grades → questions → draft verdict.

Verifier: independent critic with hard rules; it can only block, never upgrade.

Supervisor: background loop with memory (sync, re-check the cabinet, notify).

Stores

Raw snapshots (files): the exact bytes CDSCO sent, by month, plus a content-addressed archive.

SQLite: alerts with provenance, quarantine, checks (paused state lives here), cabinet, notifications, learned confusions.

Traces: one JSONL file per check for the step log.

Design vs runnable build. The spec (v2 §4) draws LangGraph graphs with SqliteSaver checkpoints, an LLM planner and Phoenix tracing. Decision D18 replaced LangGraph in the runnable release with a compact engine: investigate() returns a JSON snapshot that is stored and resumed, and traces are local JSONL. The LLM and Phoenix came back as options (D23). In hybrid mode (--planner hybrid or STRIPCHECK_PLANNER=hybrid) the local model picks the next action at two branch points, and with STRIPCHECK_TRACING=1 each check is also exported to Phoenix as one OpenTelemetry trace. Say this plainly in the viva: the agent loop is real, the default planner is rules, and the LLM is an option that never decides a verdict.

03Getting the data

Until mid-2025 CDSCO published PDFs. From August 2025 the lists moved to an online table. The table's page had no download button, so we traced where it gets its data.

GET https://cdscoonline.gov.in/CDSCO/reportingYears?tab=nsq            -> ["2019",...,"2026"]
GET https://cdscoonline.gov.in/CDSCO/publicReportingMonths?year=2026&tab=nsq  -> ["Jan",...]
GET https://cdscoonline.gov.in/CDSCO/filteredNsqDrugTable?month=SEP-2026&source=All&tab=nsq
GET https://cdscoonline.gov.in/CDSCO/filteredSpuriousDrugTable?month=SEP-2026&source=All&tab=spurious

The four calls core/portal.py makes (discover_months, then fetch_month). The month key is built as MON-YYYY and cross-checked against the stored YYYY-MM file name.

Polite scraping, as coded

What is stored for every month

data/raw/portal/nsq/2026-09.json       # exact bytes
data/raw/portal/nsq/2026-09.meta.json  # url, fetched_at,
                                       # sha256, bytes, rows,
                                       # encoding: latin-1
data/raw/archive/<sha256>.json         # never overwritten

Writes are atomic (temp file, fsync, rename). If a month is revised, the old bytes survive in the archive under their hash.

Why latin-1

The portal answers charset=ISO-8859-1. A 0xA9 byte broke a UTF-8 decode, so portal.py decodes with latin-1 and records that in the meta file. A dash typed in the source often arrives as ?, which cleaning repairs (section 4).

Offline after the first sync

sync --offline re-ingests stored snapshots only. If the network fails mid-sync, stored data stays and the status is "partial".

Why not the PDFs

PDFs stop at June/July 2025, file names are irregular, download links often return a page instead of the file, and table extraction can split or merge cells. The JSON has one row per alert, a separate brand field and covers 2019 to now. PDF helpers (pdf_lines, pdf_text_chunks) exist but are a secondary research path.

Why the data is not in git

CDSCO's copyright policy says its content "may not be reproduced partially or fully, without due permission". So data/ is git-ignored, each machine fetches its own copy, every verdict cites the source, and the paper publishes only derived statistics.

05Reading a pack

read_pack() in core/pack_tools.py turns a photo into fields, and records where each field came from. Every reader runs locally in a killable subprocess with a time limit; any failure falls through to the next reader and finally to "type it yourself".

Why OCR confidence is not trusted

What the code does instead

Confidence measures how sure the reader is of its own output, not whether the output is true. A confident misread can even land exactly on a listed sibling batch. So the score never authorises an alarm. A FLAGGED or SUSPECTED_FAKE result needs batch evidence from this set (GATE_EVIDENCE in verifier.py):

qr dual_read user_typed user_confirmed

OCR alone, at any score, is not enough: the agent asks you to type characters from the pack first (section 9).

06Finding candidates

Retrieval is blocking in record-linkage terms: cheaply pull every alert that could plausibly be this batch, then grade each one carefully. Two searches always run: the exact key, then its confusion variants.

Noisy-channel ranking

When several variants hit, they are ordered by (1) fewer substitutions, (2) a score from the learned confusion counts, (3) alert id, so the order is deterministic.

score = Σ log((n[r,t]+α) / (n[r,r]+α))
r = read char, t = true char, α = 1

With no counts the score is 0 and only the substitution count matters. Counts come from the confusions table (sources user and calibration).

Why a prior never skips the question

Suppose users have confirmed "8 was really B" many times. It is still possible that this strip really says LM24088. Real lists contain siblings like R21119 / R21719: same drug, same maker, both real batches. Statistics about OCR cannot tell which one is in your hand; only the printed pack can.

In the code a variant hit is graded needs_confirm_char, the trace says "No printed character was changed", and the status auto_corrected is never set.

07Judging a match

A batch code alone is weak evidence. grade() in core/matching.py compares four more fields, the way record linkage decides whether two records describe the same thing, and puts each candidate in one of three zones.

08How the agent thinks

Agentic means the next step depends on what the last step found. Here is the misread demo (case 03: the pack says LM2408B, OCR read LM24088) as the step log investigate() actually writes. Each row is one entry of history, with source: "rules".

The decision points

exact empty → search variants · variant hit → ask the character · exact hit but OCR-only → ask you to type characters · product missing → ask for the carton · 1-digit date difference → ask the date · bigger date difference → abstain · everything rejected and the search complete → NOT_LISTED.

Rules vs LLM planner

Design (spec §10.3): a fixed priority list (rule_next) picks the action; in hybrid mode a local LLM may choose at branch points, but only from the allowed set. Any timeout, invalid JSON or out-of-set answer falls back to rules, logged as rules(fallback).

Build: the default is rules. With --planner hybrid (or STRIPCHECK_PLANNER=hybrid) investigate() calls llm.plan_decision at two branch points: (a) the exact search came back empty, (b) a candidate needs a person. The model returns {thought, action} under a JSON schema whose action enum is the allowed set; 15 s per try, 2 tries, localhost only, 30 s pause after a connection error. The step's source shows llm or rules(fallback), and the thought is kept in the trace only.

09Asking the human

The person holding the pack is the only sensor that can resolve a doubtful character. All question wording is in question() in core/templates.py; every question offers "Can't tell".

Why typed characters and not a "Yes" button

Budgets

At most 2 questions per check (MAX_ASKS); every answer, including "Can't tell", uses one. A declined kind is never asked again. Cabinet re-checks never ask. Typed-batch checks (text mode) ask only confirm_field or box_photo, because a typed batch has no OCR doubt.

Typical cost: misread pack 1 question; clean OCR flag 1; QR flag 0.

Fixed gap, worth knowing for the viva. confirmation_positions used to ask only the first two confusable characters. If the misread was elsewhere (for example the 4th character of R21719 read as R21119), typing those two could confirm the wrong batch. Since D25 it asks every look-alike position, ordered by the confusion counts; "Type the whole batch" still works.

10The verifier and failsafes

The Verifier (core/verifier.py) is a separate, deterministic critic. It sees the draft verdict and the evidence state and checks hard rules. It can only block: on any violation the result is re-rendered as CANT_VERIFY with the list of broken rules attached.

RuleChecks (as coded)
R1label is one of the four
R2a flag needs: candidate status accept, batch exact or confirmed, batch evidence in {qr, dual_read, user_typed, user_confirmed}, product match (or partial match when dates and maker both match, the same rule grade() uses; aligned in D25), no mismatch anywhere, pack batch key = alert batch key
R3SUSPECTED_FAKE if and only if the alert is SPURIOUS
R4NOT_LISTED needs a grounded batch, exact and variant searches done, no pending or accepted candidate, data loaded, not truncated
R5a flag cites the alert with a source URL or snapshot hash; no banned phrase in headline, explanation or advice
R6steps ≤ 16, questions ≤ 2
R7an unresolved date conflict allows only CANT_VERIFY
R8every field used has provenance user, ocr, qr, ocr_enh, carton or vlm
R9NOT_LISTED states the lists loaded and the latest month
R10language is English (reviewed translations are not available yet)

Abstention is an answer

CANT_VERIFY always carries its reason: batch not provided · incomplete batch · photos disagree · date unreadable · step limit · date conflict · too many records share the batch · needs product/maker/date evidence · "Possible match: if your batch reads …" (batch gate) · verifier rules.

Safety language

BANNED blocks safe, genuine, authentic, fake medicine, stop taking/using and Hindi equivalents. Any text taken from data passes clean_text, which replaces those words with "[word omitted]". Every result ends with the fixed pharmacist advice. NOT_LISTED says "This does not certify the medicine" and is slate, never green.

11Memory and feedback

Two kinds of memory persist between checks, both in SQLite and both owned by core/supervisor.py.

What memory may not do. A learned correction only reorders candidates and chooses question positions. It never changes a printed character, never skips a question and never lowers the batch gate. Demo checks never write to memory.

14Viva cheat-sheet

The 18 questions from the project plan (§10.3), with answers that match the code. Where the plan's model answer describes the research design rather than the build, the answer says so: examiners reward knowing the difference.

1. Why is this agentic and not a script?

The next step depends on what the last tool found. Exact search empty → variant search. Variant hit → ask the character. Exact hit but read only by OCR → ask you to type characters. Product missing → ask for the carton. One-digit date difference → ask the date; bigger → abstain.

A script does one lookup: it false-alarms on shared codes like 8S17004 and misses a misread like LM24088.

2. Where is the planning loop?

In investigate() (core/investigator.py). After each tool result it picks the next action, can pause for a question and resume from the saved state. Every step is logged with action, source, summary and time.

With the default planner every step's source is rules. In hybrid mode the local model chooses at two branch points (empty exact search; a candidate that needs a person), only from the allowed actions, and those steps show source: llm with a one-line thought. The spec's LangGraph graph was replaced by this engine (D18).

3. What makes the retrieval "agentic RAG"?

The agent chooses the queries: the exact key, its confusion variants, and new keys after your answer (a typed or corrected batch). It grades every candidate on product, brand, dates and maker, and re-queries after new evidence.

When the evidence stays weak it abstains instead of answering. Searching by product name when no batch is readable is in the spec, not in the build; the build asks you to type the batch.

4. What happens when OCR is confidently wrong?

Confidence cannot catch it: we saw a scuffed B read as 3 at confidence 1.0. Exact search fails, variant search finds the listed key one confusable character away, and the person confirms that character (confirm_char).

If OCR lands exactly on a listed key, the batch gate still asks you to type characters before any alarm.

5. Why not auto-correct once users confirmed the same error twice?

Sibling batches exist: R21119 and R21719 are the same drug from the same maker. 58 such same-maker pairs were in the Oct 2026 data.

A prior only says what OCR usually gets wrong, not what this pack says. In the code the prior reorders candidates and picks question positions, and auto_corrected is never set.

6. How do you avoid false alarms?

A flag needs all of these:

  • a cited alert with status accept, meaning an exact or confirmed batch, a product match, dates or maker matching, and no mismatch;
  • batch evidence from QR, two agreeing reads, or the person;
  • verifier rule R2 passing.

Collisions are rejected on the field that mismatches.

7. What does NOT_LISTED mean?

Only that no entry matched on the lists loaded. The verifier (R4) also requires a grounded batch, exact and variant searches done, and no candidate still pending or accepted. The text states how many lists are loaded and the latest month (R9).

CDSCO tests only sampled batches, so the result never certifies a medicine and is never shown in green.

8. What does the LLM do, and what if it's off?

Design: it plans at branch points, extracts fields when regex fails, adjudicates partial product matches, maps changed headers and repairs rows, always with a rules fallback.

Build: only planning is on the check path, and only in hybrid mode. llm.plan_decision (localhost only, 15 s, 2 tries, JSON schema with the allowed actions as an enum) picks the next action at two branch points and writes a thought into the trace. On the 60-carton evaluation it gave the same label as rules on every pack, with p95 latency 8.96 s vs 1.86 s. Field extraction, adjudication and header repair by LLM are not built. With Ollama off, the planner falls back to rules (rules(fallback)) and the check finishes normally.

9. How do you stop the LLM hallucinating?

In the build no model writes a field or a sentence. Fields come from QR, OCR or the person, each with provenance (verifier R8). All user text comes from templates.py, and the BANNED filter plus R5 block assurance words.

The hybrid planner forces a JSON schema and an enumerated action set, treats pack text as untrusted data, and its thought only goes to the trace; a thought with a banned word is withheld.

10. How are loops bounded?
  • Per check: 16 steps (the plan said 12), 2 questions, 1 enhanced re-read per image, 2 substitutions per variant, 2,000 variant lookups, 20 candidates.
  • Time limits: OCR 60 s per image, QR 20 s, network 20 s × 3, LLM 15 s × 2.
  • Ingest: 16 MB and 100,000 rows per snapshot, 1,000 files per run.

The verifier sends a draft back once only when the LLM planner drafted before the variant search; any other violation becomes CANT_VERIFY at once.

11. What are the agents?
  • Supervisor: background work: sync, ingest, re-check the cabinet, notify.
  • Ingest: turns the lists into a validated index and quarantines bad rows.
  • Investigator: checks one pack.
  • Verifier: the critic with hard rules.
12. How does ingest cope with CDSCO changing its format?

Several checks protect the data:

  • The response must hold an aaData or data list, or the stored data is kept.
  • Field names have fallbacks (str_product_name or product_name_from_dtl …), and map_headers knows header synonyms for tables.
  • Rows that fail validation are quarantined with reasons, and the cleaning version forces a re-clean when the rules change.

The LLM header mapping tested on 5 sample rows is spec design, not built.

13. What is durable here?

Checks: the whole engine state is a JSON snapshot in SQLite (WAL), so a check can wait for your answer and resume by its thread id after a restart.

Ingest: each file is one transaction, imports are idempotent by row hash, and snapshot writes are atomic. There are no LangGraph checkpoints in the build.

14. Where is memory?

Two places. The cabinet holds saved packs that are re-checked after each sync, with deduplicated notifications and expiry reminders.

The confusions table holds learned corrections from your answers. They are used to rank variants and pick question positions, and are shown in the trace.

15. How was the golden set built, and why trust it?

60 cartons rendered from real CDSCO alert rows in the local index, deterministic from seed 7 (seed 1 for development): 8 each of clean, glare, misread, QR, spurious, collision and unlisted, plus 4 sibling traps. Every image carries the banner "DEMO PROP - NOT A MEDICINE". Misread and sibling cartons print the misread string, so OCR error is simulated, and the oracle answers from the intended batch.

Why trust it: every row is a real alert, the OCR read matched the rendered text on 60/60 images, and the generator is seeded and rerunnable. Why not trust it too far: rendered cartons are easier than foil, and there are no real strip photos. The 11 authored diagnostics still run in the test suite (section 12).

16. What was the A/B result and decision?

With the person answering, the agent removed every collision and sibling false alarm (lookup 8/8 and 4/4, agent 0/8 and 0/4) and found 40/40 listed batches against 32/40 for the lookup, at 0.60 questions per pack. R-A: adopt (McNemar p = 2e-06). With nobody answering it abstains on 36/60 packs, hit recall drops to 8/40, and R-A says do not adopt: the questions carry the recall. R-C holds on its terms, but hybrid adds tail latency and changed no label, so rules stay the default.

Say the honest part too: the first run on the same seed gave 33/40 and also adopt; two predictions failed. Three general bugs were fixed after that run (section 12), so the second run's numbers are optimistic.

17. Biggest limitation?
  • The answer is only as current as the lists loaded; a normal sync covers the latest 3 months, and history needs --full.
  • CDSCO tests only sampled batches.
  • Labels and templates are English-only.
  • The evaluation is synthetic (rendered cartons, no real strip photos), and the reported run came after fixes made on the same seed, so its numbers are optimistic.
  • OCR on shiny foil is hard.
  • Asking every look-alike position (the D25 fix for a gap in section 9) is safer but makes some questions longer.
18. Ethics?
  • Advisory wording only. It flags the listed batch, never a brand, and cites the source.
  • It abstains under uncertainty and sends people to a pharmacist.
  • Photos and data stay on the laptop, and no personal data is collected. LAN access needs a pairing token.
  • CDSCO data is kept local, with only derived statistics published.

15Glossary

CDSCO
Central Drugs Standard Control Organisation, India's national drug regulator.
SUGAM portal
CDSCO's online system at cdscoonline.gov.in; its public viewer serves the NSQ and spurious lists as JSON.
NSQ
Not of Standard Quality: a sample failed a lab test (assay, dissolution, sterility…).
Spurious
A product that imitates or claims to be made by someone else. StripCheck says "purported spurious".
Batch / batch key
The printed lot code; the key is its upper-case letters and digits only (CBC-0012/25 → CBC001225).
GS1 AI
Application identifier in a barcode: (01) GTIN, (10) batch, (11) mfg, (17) expiry, (21) serial.
Snapshot
The exact bytes of one month from the portal, stored with URL, time, SHA-256 and row count.
Quarantine
Rows held back with reasons and raw JSON instead of being guessed at.
Row hash
SHA-1 of the canonical raw row plus month, kind and batch; makes re-imports idempotent.
Confusable
A character OCR often swaps for another (B/8/3, 0/O/Q/D, 1/I/L/7…), from the CONFUSABLE table.
Variant
The read key with one or two confusable characters swapped; used only to find candidates.
Blocking
Record-linkage term: a cheap step that limits which records are compared in detail (here, exact and variant keys).
Record linkage
Deciding whether two records describe the same entity by comparing several fields; zones: match, possible match, non-match.
Collision
Two unrelated products listed under the same batch code.
Sibling batch
A batch of the same product and maker one character away (often sequential numbering).
Noisy channel
Model of how a true character becomes a read character; used to rank variants by likelihood.
α (smoothing)
Pseudo-count added to every confusion count (α = 1) so unseen pairs are not impossible.
Provenance
Where a field came from: qr, ocr, ocr_enh, carton, vlm or user.
Batch gate
The rule that a flag needs batch evidence from qr, dual_read, user_typed or user_confirmed.
dual_read
Two independent readers (for example strip and carton) agree on the batch key.
HITL
Human in the loop: the person answers a bounded number of questions.
Habituation
People stop reading repeated confirm dialogs and click through; why StripCheck asks for typed characters.
Abstention
Answering CANT_VERIFY with a reason instead of guessing.
Verifier
Deterministic critic applying rules R1 to R10 to every draft verdict.
Cabinet
Saved packs that are re-checked automatically after each list sync.
SQLite WAL
Write-ahead logging: readers keep reading while one writer commits.
SSE
Server-sent events: the server streams each agent step to the page over HTTP.
Ollama
Local runner for open LLMs; optional in StripCheck.
VLM
Vision-language model; designed as an optional second reader, never sole evidence.
LangGraph / Phoenix
Agent-graph framework and tracing tool in the research design. LangGraph was replaced by the resumable engine (D18); Phoenix stays as an optional OpenTelemetry export next to the JSONL traces (D23).
Golden set
Seeded, labelled synthetic packs used for the preregistered evaluation.
McNemar test
Paired test for two systems on the same items: counts where only one of them is right.
Wilson interval
A 95% confidence interval for a rate that behaves well near 0% and 100%.
PPV
Positive predictive value: of all FLAGGED results, the share that are truly listed; falls sharply when listed packs are rare.
